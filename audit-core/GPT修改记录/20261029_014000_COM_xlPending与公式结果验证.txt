目的

按用户授权优化 Windows Excel COM 公式重算判定，并确认 S1-F1 公式缓存及结果值不是仅凭 COM API 返回成功而接受。

发现

- sidecar 在重算请求中设置 `fullCalcOnLoad=1` 和 `forceFullCalc=1`。Excel COM 对含两项标记的文件在 `CalculateFull()` / `CalculateFullRebuild()` 后仍可能持续返回 `xlPending`。
- 受控 Excel COM 探针显示，原公式结果实际已在内存计算并可读，包括 `#DIV/0!`、`#REF!` 及文本值；普通公式错误并非计算失败原因。关闭两个加载标记后，清除缓存的文件仍可由显式全量计算和依赖重建得到 `xlDone`。

修改

- `sidecar/lo-convert/src/main.rs`：Windows COM 路由从全量重算请求副本再创建专用临时输入，将 `fullCalcOnLoad` 和 `forceFullCalc` 置 false；验证公式仍存在且没有任何旧公式缓存，再交给 PowerShell + Excel COM。COM 仍执行 `CalculateFull()`、`CalculateFullRebuild()`，只有 `xlDone` 才保存。
- LibreOffice 路由继续接收 `fullCalcOnLoad=1`、`forceFullCalc=1` 的重算请求；不改变 Linux 调用策略。
- 保存后验证工作表顺序、每张表公式文本不变、每个公式都有缓存节点，且 Calamine 为每个公式读到带类型的结果值。错误结果和公式返回的空字符串都保留为可读结果。
- 新增单测覆盖 COM 输入标记、缓存清空、公式结果覆盖、错误值/空字符串和缺失值拒绝。
- 更新 `DEVELOPMENT_GOAL.md` 与 `audit-core/MIGRATION_INVENTORY.md`：记录 COM `xlPending` 原因、COM/LO 分工和本轮实际验证范围。
